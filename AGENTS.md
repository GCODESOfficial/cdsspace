# Workspace instructions

- When a task requires applying SQL or a database migration, run it against the database connection URL resolved from this repository's `.env` file; do not stop after only creating the SQL file.
- Prefer `GLASHDB_DIRECT_URL`, then `DIRECT_URL`, `GLASHDB_DATABASE_URL`, or `DATABASE_URL`, in that order.
- Never print, log, commit, or expose the database URL or its credentials.
- Never delete, remove, unset, blank, or overwrite any environment variable or credential from a local `.env` file or a hosting provider. If a variable is temporarily unnecessary, preserve its exact value and comment out the complete local line. Because hosted environment stores do not support comments, do not remove the hosted variable; if it must be deactivated, first preserve the exact value under a clearly named disabled key such as `<KEY>_DISABLED`, and only do so with the user's explicit approval. Never replace a recoverable credential with an empty placeholder.
- Before executing SQL, confirm the resolved target and scope using non-secret metadata, and verify the affected database state afterward.
- Do not use decorative AI-style starburst motifs anywhere in the product UI. This includes the Lucide `Sparkles`, `WandSparkles`, and `Stars` icons and decorative glyphs such as `✨`, `✦`, and `✧`. Choose a restrained, context-specific professional icon instead (for example `PenLine` for drafting, `CalendarRange` for subscriptions, or `BadgeCheck` for verification). A plain `Star` icon is allowed only when it communicates an actual rating, favourite, featured, or starred-message state.
- Every user-facing share action for a shareable resource must use `src/components/share/UniversalShareButton.tsx`. The menu must retain copy link, WhatsApp, LinkedIn, Facebook, X, Telegram, email/native sharing, and authenticated in-app destinations for team groups, team members, and client chats. Do not add standalone browser-native share handlers or one-channel share buttons. Internal-only resources may use a restricted in-app share flow when exposing a public link would weaken access control.
- Public share URLs must be stable tokenised routes. Never expose private storage object URLs, database IDs, credentials, or temporary signed URLs as the permanent link being shared.
- Every editable client, team, and admin dashboard workflow must autosave unfinished work and restore it after refresh or return navigation. Use a debounced, idempotent server-side draft/upsert for structured or business-critical workflows, keep one evolving draft instead of creating duplicates, show a quiet saving/saved/error state, and delete or archive the draft after successful completion. The shared dashboard autosave layer is only a refresh-safety fallback for ordinary fields. Never persist passwords, authentication secrets, payment-card or bank fields, one-time codes, or file-input contents in browser storage; upload files immediately through an authenticated server endpoint and retain only their protected storage paths in the server draft.
- Validate print artwork compatibility by aspect ratio, not absolute pixel dimensions. Banner raster artwork within 20% of the selected print ratio is manageable and may pass; retain file-byte limits, format checks, private storage, and decompression-bomb protection. Do not apply the banner-ratio rule to reference assets such as logos.
- Use the CDS Space primary solid blue (`#0A4FE8`) for primary actions, branded panels, cards, and form accents. Do not use blue gradients in the product UI; replace legacy blue gradients with the solid primary blue and use restrained opacity, borders, or shadows for hierarchy.
- Dashboard UI must follow the CDS Space admin-dashboard visual language: sentence-case headings and labels, restrained font weights, normal letter spacing, soft surfaces, clear hierarchy, and smooth mobile-responsive layouts. Do not use all-caps headings, buttons, status filters, tracking labels, or decorative wide letter spacing unless the text is a genuine short identifier or acronym (for example an invoice number, currency code, or user ID). Apply this consistently across client, team, marketer, and admin dashboards and use the admin dashboard as the benchmark for future dashboard work.
- Use Next.js `Link` from `next/link` for every same-origin application-page navigation, including dynamic internal routes and internal routes intentionally opened in a new tab. Do not use a raw `<a>` or `window.location` for ordinary internal page transitions because they trigger a full document reload. Keep raw anchors for external URLs, `mailto:`, `tel:`, hash-only jumps, downloads, and API/document endpoints; reserve `window.location` for flows that require a document-level navigation such as OAuth, payment-provider redirects, login/session handoffs, logout, or account closure.
- Public authentication gateways must not serve long-lived cached HTML that can reference obsolete deployment chunks. Keep login, signup, recovery, and related auth shells dynamic or explicitly non-cacheable, and provide runtime fallbacks for optional browser APIs such as `requestIdleCallback` so Safari, iOS, embedded webviews, and older supported clients cannot crash during hydration.
- Dashboard route changes must keep the shared shell, sidebar, header, and persistent providers mounted while only the route-content region changes. Pathname-dependent authentication, permission revalidation, loading, denied, and transient-error states must render inside the content region after the first session check; never replace the entire authenticated layout during ordinary navigation. Keep rendered shell component identities stable across pathname updates so menu expansion, scroll, and local UI state are preserved.
- Dashboard authentication invariant: after any login gateway succeeds, client, team, marketer, admin, and every future dashboard must navigate using one durable first-party HTTP-only session tied to the stable internal user ID. Provider/OAuth tokens may establish or refresh that session but must never be paired as a second per-navigation requirement. Validate signature or opaque token, audience, expiry/revocation, user-ID ownership, and current account status server-side; only an explicitly missing, invalid, expired, revoked, mismatched, suspended, or closed session may redirect to login. A transient provider, refresh, database, or network failure must not log out an authenticated user. Login must rotate or replace the first-party session, logout/account closure must clear or revoke it, and regression coverage must prove that valid session-only navigation works across pages.
- Staff portal switching invariant: an authenticated, active team member with admin access must move between the team and admin portals without another login prompt. Each direction must complete a server-verified first-party session handoff before navigation, reuse an existing valid same-identity destination session instead of rotating it, and verify the stable team-member ID, active status, admin entitlement, expiry/revocation, and cookie ownership; normalized email is permitted only as a compatibility fallback for older admin sessions that predate stable member IDs. Never reuse a destination session belonging to a different identity. Transient bridge, database, or network failures must preserve both sessions and show a retry state instead of redirecting to login. Explicit staff logout must revoke or clear both team and admin portal sessions. Regression checks must cover both switching directions, same-session reuse, and cross-identity rejection.
